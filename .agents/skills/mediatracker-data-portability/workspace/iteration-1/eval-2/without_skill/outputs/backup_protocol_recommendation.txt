While you technically can copy the .db file, it is strongly discouraged for MediaTracker. Because the app uses SQLite in WAL (Write-Ahead Logging) mode, a raw file copy often results in an inconsistent snapshot if there are pending transactions or recent committed changes not yet checkpointed residing in the accompanying .wal file.

Instead, the project mandates the SQLite VACUUM INTO protocol for all backups.

### Recommended Backup Protocol

1. Use VACUUM INTO: Always use the VACUUM INTO 'path/to/backup.db' command. This creates a consistent, defragmented single-file snapshot of the database, even while it is actively being written to. It provides a consistent snapshot at the moment the command runs, though it is not an atomic publication to the final destination unless explicitly moved there after validation.
2. Google Books Key Scrubbing: Before the backup file is handed to the user or exported, DatabaseBackupUseCase must remove the Google Books API-key row from the staged snapshot to maintain privacy.
3. Verification on Restore: When restoring a backup, the app must:
    * Validate the first 100 bytes of the file (SQLite magic string and user_version).
    * Execute PRAGMA integrity_check to ensure the file is not corrupt.
    * Only swap the live database file after these checks pass.

This protocol ensures user data safety and prevents the "silent corruption" that can occur with simple file copies of active databases.
